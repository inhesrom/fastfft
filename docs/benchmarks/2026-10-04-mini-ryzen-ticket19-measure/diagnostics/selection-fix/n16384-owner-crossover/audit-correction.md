# N16384 audit expectation correction

The retained capture passes the corrected diagnostic audit: eight trial summaries, 18 quiet running samples, no problems. This remains diagnostic evidence (`acceptance: false`). No FFT, build, timing, Rust edit or raw-data change was performed for this correction.

The only signature mismatch was the outer `Object.element_bytes`: every Estimate and Measure owner in all eight trials reports **192**, while the new N16384 audit had copied **272** from the legacy captures. `source/crates/fastfft/src/fft.rs:217` calls `DiagnosticRegion::object(self)` on `FftImpl`; `source/crates/fastfft/src/tuning.rs:638` computes `size_of::<T>()`. Therefore this region describes the complete compiled FFT object, including its Kernel enum, not just Stockham's 112-byte embedded plan or its coefficient owner. The compact canonical FourStep variant changes that enum's layout even for a Stockham object. The frozen executable's emitted size is 192; Rust representation does not promise this size across builds, so this is a fixed capture expectation, not a newly invented ABI formula. The embedded Stockham starts at byte 8 and ends at 120, within 192.

The auditor now fixes N16384's expected outer size at 192 and uses that same fixed size for embedded-plan containment. It still rejects any other size; the legacy N75600/N165375 expectations stay 272. All 17 other N16384 region signatures already matched and remain unchanged.

Source-derived coefficient calculation (`engine/stockham/storage.rs:52`, `engine/stockham.rs:228`): four 24-byte pass descriptors occupy 96 bytes, rounded to 128. For radices 8,4,8,8, `2*ns*(radix-1)` gives scalar lengths 14,48,448,3584. Aligning each start to 64 bytes gives offsets 128,192,384,2176; Phase B starts at 16512. The recorded owner, descriptor/radix views, pass tables and Phase B all satisfy these exact expectations.
